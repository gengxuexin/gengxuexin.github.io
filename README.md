## 改版流程

```bash
# 1. 在工作副本改
cd 个人网站/
vim index.html

# 2. 本地预览
python -m http.server 8899 --bind 127.0.0.1
# → http://127.0.0.1:8899

# 3. 链接自检（浏览器实测）
python -u _check_links.py http://127.0.0.1:8899/index.html

# 4. 同步到发布目录并推送
cd ../个人网站-发布/
cp ../个人网站/index.html .
cp -r ../个人网站/assets .
git add -A && git commit -m "docs: 更新站点内容"
git push
```

推送后约 1 分钟生效。

## 三条硬规则

### 1. 资源文件一律用 ASCII 文件名

中文文件名在 HTTP 路径下会 **404** —— 浏览器把 `庚雪鑫-简历.pdf`
编码成 `%E5%BA%9A%E9%9B%AA...`，多数静态服务器（GitHub Pages、
WorkBuddy 预览面板、部分 CDN）不认这种路径。

> 实测：同一文件用 `python -m http.server` 能 200，用 GitHub Pages / 预览面板 404。
> **别被本地能打开误导。**

页面上的**显示文字**用中文没问题，**只有文件路径要避开中文**。

### 2. 站点不提供简历下载

按要求已移除全部下载入口与 PDF 文件。简历通过邮件或 GitHub 主页索取。

### 3. 网页数字必须与简历一致

唯一真相来源是用户提供的简历 PDF 原文
（`D:\Software\微信聊天记录\...\庚雪鑫20261024_20261026181701.pdf`，2 页）。
**改任何数字前先对简历**，避免出现「网页一套、简历另一套」。

## 踩过的坑（记录以免复发）

**坑 1：Edge `--print-to-pdf` 遇中文文件名 + 相对路径会静默不覆盖。**
报 "written" 但旧文件纹丝不动 → 曾据此误判「排版改动无效」。
必须先 `rm` 再生成，且用绝对路径。

**坑 2：屏幕宽度 ≠ 打印宽度。**
浏览器量到 bodyH 1966px，但打印时 A4 减页边距只有 190mm 宽（719px @96dpi），
文字重排后变高 → 页数比预期多。判断能否装 2 页要按**打印宽度**测：
`Emulation.setDeviceMetricsOverride({width:719,height:1046})` 再读 scrollHeight。

**坑 3：`break-inside: avoid` 会级联。**
给长表格加 `avoid` 会导致整表推到下一页，前一页留大片空白。
只给短表格/短卡片加。

**坑 4：预览面板是快照，不反映新文件。**
WorkBuddy 预览面板的文件清单在首次 present 时固化，
新增文件即使 present 过也可能 404 —— 要用独立服务器（如 `python -m http.server`）验证。

## 踩过的坑：裸 `<script>` 标签吞掉半个页面

**现象**：用户反馈「最后这个只有一个字」——
「怎么做的」区块的验证机制表，最后一行「JS 语法门禁」的第三列只显示一个「抽」字。

**实际影响远不止一行**：那一行下面还有**三个完整区块**（工程判断力 / 技术栈 / 联系），
在渲染后的 DOM 里**全部消失**。页面总高只有 12,252px，修完是 16,159px。

**根因**：表格里为了说明 `node --check` 的用法，写了字面量

```html
<code><script></code>
```

浏览器从那个裸 `<script>` 开始，把后面所有内容当成脚本文本处理——
包括 `</table>`、`</section>`、`</body>` 全都成了脚本的一部分。

**为什么之前没发现**：

| 检查方式 | 结果 | 为什么测不出来 |
|---------|------|--------------|
| `grep '<section'` 源码 | 7 个都在 | 源码确实没问题，问题是浏览器怎么解析 |
| 资源链接 fetch | 全部 200 | 图片和 CSS 都在下半页，但**它们在 script 标签外面**，所以照常加载 |
| 我原来的 `_check_links.py` | 通过 | 它只查资源可达，**跳过了 `#` 锚点**，也没查 DOM 结构 |

关键在于：**「链接都能打开」不等于「页面完整」**。
资源正常 + 源码正常 + 页面残缺，三者可以同时成立。

**修法**：

```html
<!-- 错 -->
<code><script></code>
<!-- 对 -->
<code>&lt;script&gt;</code>
```

**门禁**：`_check_links.py` 升级为三维检查——

| 维度 | 查什么 |
|------|--------|
| 资源可达 | 每个 `a[href]` / `img[src]` 逐个 fetch 看 HTTP 状态 |
| 锚点有效 | 每个 `#anchor` 在渲染后的 DOM 里真有对应 `id` 元素 |
| **结构完整** | **源码里每个 `id="..."` 必须在渲染后的 DOM 里存在** |

第三条是这个 bug 逼出来的。已用**带 bug 的回归样本**验证门禁有效：
复现时准确报出「3 个 id 丢失 + 3 个区块缺失 + 3 个锚点失效」，
且**资源全部 200 也不影响判定为失败**。

> 这条和消防项目那条「验收脚本只验存在性、不验可用性」是同一个教训：
> **检查工具本身需要被检查。**
> 上次是 grep 字符串存在就算过，这次是资源 200 就算过。

这一节讲的是「人」而不是「技术」，来源是一份自我介绍初稿。

直接放进去会自相矛盾。**

所以每一条软实力都配了一个 **「对应实践」** 落点，

单独用 `.soft-item-final`（蓝框 + 浅底 + 跨两列）强调。
