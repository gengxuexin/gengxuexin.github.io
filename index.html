消防智能执法多模态 Agent 系统 已实现

2026.05 – 2026.10 · 深兰科技 Python / FastAPI / LangGraph / FAISS 19,643 行 · 393 测试 · 57 验证脚本 github.com/gengxuexin/inspection-multi-agent-fire-agents ↗

消防执法文书高度模板化，但每次制作要 40~60 分钟且极易出错 —— 引用错一个条款号，文书就得退回。我把它做成四个服务： 网关（鉴权/审计/限流/三级级联路由）+ 法规 RAG（103 份文档 → 4,019 分块）+ 语音（ASR/TTS）+ 视觉（YOLO/OCR），34 个 API 端点， docker-compose 一键拉起 7 个容器。

我的主要工作

  1. 建立评测可信度机制（核心产出）
    发现连续三轮评测的检索上下文逐字完全相同 —— 属空跑， 分数差异 0.004~0.021 全落在 LLM 判分抖动量级（实测 0.021）以内， 而我当时把那个结论写进了文档。遂建立三道机制： 上下文指纹（只哈希检索结果，不含答案与分数）、 空跑阻断（指纹一致只报「不能作结论」，不报「这是空跑」）、 噪声底 0.05（单次 A/B 差值只是抖动幅度的下界，不是幅度本身）。 相关逻辑 30 个单元测试覆盖。
  2. 分块层的根因治理
    检索不到某个产品条目，逐层排查发现答案完整存在于一个 306 字 chunk 里、 BM25 明确排第 1 名，却被挤出 top-k。根因是 PDF 视觉结构转纯文本后丢失， 「一个条目 = 一个语义单元」被破坏。 判据改了 3 版才对：目录类文件独占标准号行占比 9.00% / 5.61%， 而导则类只有 0.15% —— 差 37 倍，阈值取 2% 留足余量。
  3. 发现并治理引用编造
    实测 10 个问答中仅约 20% 的法条引用可溯源至检索片段， 且同一问题跑两次结果不同（随机波动，非稳定能力）。 建立三道防线（生成约束 / 审核标记 / 归档确认）， 并把弃答判定由二元改为三态（可答/存疑/未知）—— 不把猜测写成事实。
  4. 三轮精排 A/B 与一次回退
    每轮只改一个变量。其中一轮结果与前一轮逐位相同， 一次实验排除了一整类假设。过程中用候选池重叠度分析定位到 「单个 IDF 常量同时污染 BM25 召回与精排排序」的变量隔离缺陷。 最终三轮全部判定不上线 —— 根因是取舍而非 bug： idf² 优化单文档精确定位却伤害跨文档综合问题。 保留结构改进，回退效果部分。
  5. 生产化
    三态熔断、token 预算闸门、LLM 主备链（DeepSeek → 通义千问， 13 个业务文件零改动）、11 项 Prometheus 指标 / 19 个 Grafana 面板 （含高基数防护）、Agent3 镜像从 11.3GB 瘦身到 3.84GB。

后续规划

上面是已交付的部分。往下走的方向有三条，且有先后依赖 —— 顺序错了，做完也看不出有没有用。

  • 先把评测立住，再动检索
    现有评测集撑不起细粒度 A/B —— 差异小于噪声底时，结论不成立。 先扩样并把弃答样本单独统计（它与检索能力是两件事）， 再优化检索才有可信的反馈信号。 检索侧的方向是查询分解与多路联合召回，重点攻跨文档综合类问题。
  • 把治理从「一刀切」变成分级
    高危操作现在统一人工确认 —— 安全，但业务量上来就是瓶颈。 改为按风险分级（查询自动 / 可逆单人 / 不可逆双人）， 并做审批权限分离：生成文书的人不能审批自己的文书。
  • 从单次执行走向规模化
    熔断与限流状态跨实例共享、容器内链路健康检查与滚动发布， 让多节点下的故障隔离行为一致； 并支持多轮追问，按案件分区隔离状态。

食品工厂 HACCP 巡检整改多 Agent 闭环系统 已实现

2025.11 – 2026.03 LangGraph / RAG / VLM / FastAPI / SQLite 5,381 行 · 31 测试 · 三套离线评测 github.com/gengxuexin/inspection-multi-agent-foodfactory-agents ↗

针对食品工厂巡检三个真实痛点：问题与 HACCP 条款对不上（查表慢）、 人工分级容易错、口头答应但表上假改。 架构不是「多个 Agent 自由对话协商」，而是 Orchestrator + 共享状态 + 条件路由 + 硬闸门 + Human-in-the-loop。

三条不可绕过的硬约束（写在代码里，不只写在文档里）

  1. 低置信度条款映射不得自动定级
    置信度由多信号合成（rerank 归一化分数 + 双路一致性 + 元数据匹配）， 单看向量分数无法区分「检索偏了」和「条款库缺项」。 三档分流：≥0.75 预填（可改）/ 0.50–0.75 展示 Top-3 必须人工选 / <0.50 显式弃答转人工。
  2. A 级 / CCP 问题不得仅凭照片自动关闭
    20 条可执行规则决策表（A01–C04）并行评估取最高等级。 规则全未命中时 LLM 才给建议，但 LLM 不能单独定 A 级；证据不足默认不低于 B； 人工降级必须填理由，原等级保留供复盘。
  3. 打回整改不重置倒计时
    打回 → 无效整改次数 +1，deadline 不变 → 超时照样升级。 连续打回 2 次自动升级一级响应，3 次通知厂长/质量总监。 延期与打回独立，打回不能作为延期理由。

证据验证：五道闸门

清单完整性（缺项打回）→ 元数据（EXIF 早于派单即疑似旧图打回；无 EXIF 判存疑， 不误杀）→ 历史复用（sha256 一致打回，pHash ≥0.95 打回， 0.85–0.95 存疑）→ VLM 语义核验（结构化 match/mismatch/uncertain， 仅对明确不符自动打回）→ 交叉校验（与 MES/设备日志矛盾则存疑）。 任一道打回即终止，但打回不重置倒计时。

图像分类的域差治理（这个项目最反直觉的发现）

接入公开的 SigLIP2 模型（官方指标 91.8%）与自训 Fashion-MNIST 小型 CNN （测试集 3000 张，准确率 86.70%）。 实测发现公开模型在真实商品照上识别错误， 而且以 0.95~0.99 的高置信度误判。三组对照实验定位根因：

对照实验结果结论
SigLIP2 跑 Fashion-MNIST 原图10 / 10 ✓模型与加载链路完全正常
SigLIP2 跑实拍图（224×224）0 / 4，全判「单肩包」域差
实拍图先降采样到 28×28 灰度再放大仍 0 / 4不是分辨率问题，是图像域问题
根因：SigLIP2 是在 Fashion-MNIST 的白底平铺小图上微调的， 它学到的是「小图中央的深色块 = 包」。真人穿着的照片缩到 224×224 后语义完全变了。

由此得出的工程判断：公开指标高 ≠ 实际场景能用。 所以后端优先级不按模型强弱排，而按在自己业务数据上的实测效果排 —— 建立后端可信度注册表，只有业务数据实测达标的后端才允许参与决策，并做多后端交叉验证。 主判定原型 KNN 在真实商品照上正确识别率上升到 98%，单张端到端约 10ms。

另一个细节：不可信后端不再被加载，延迟从 300ms 降到 11ms —— 「不采信」本身就是性能优化。

基于毕业设计的 29 组实验数据（9 组单因素 + 18 组正交）， 把辣酱配方研发从「经验试错」变成「模型预测 + 定向优化」。

模块做法结果
配方优化 分层建模：单因素 → 二次拟合（边际效应），正交 → GPR（全局稀疏高维） 留一验证 R²=0.642 / MAE=1.93 分；推荐 5 个新配方，预测评分高于实验最优值
货架期预测 用菌落总数生长曲线（Logistic）预测保质期 R²=0.9915，预测 7.4 天达 10⁵ CFU/g，与实验观察一致
最有价值的技术判断：数据要分开建模
两类数据的生成机制不统一（单因素是局部变化，正交是全局变化）， 混在一张拟合面上会互相干扰，R² 会变负。 分开处理后各自发挥优势。

为什么选 GPR 而不是随机森林？因为 GPR 提供不确定性估计 —— 贝叶斯优化需要同时知道「候选点的预测值」和「预测值的不确定度」， 才能用采集函数（EI/UCB）决定往哪探索。 9 个样本做 GPR，虽然数据少，但每个预测点都带着标准差， 优化器就能在「有希望但不确定」的区域多看几眼 —— 这比在稀疏数据上硬套一个没有不确定性的模型靠谱得多。
05 / How I Work

我是怎么做的

上面是结果，这里是过程。我的工作方式可以概括成一句：让 AI 产出候选，让机器决定什么算对，让脚本保证结论不漂移。

四步闭环

① 先定义「对」是什么 写出可执行的判定标准（测试、脚本、指标） 判定标准不成立时，不接受任何 AI 产出 │ ▼ ② 让 AI 在约束下产出 上下文给足：相关文件 · 已有模式 · 明确的失败案例 一次只让它改一件事 要求它自己先说清楚「怎么验证」 │ ▼ ③ 用机器验证，不靠「看着对」 pytest / 验证脚本 / 实跑 Demo 失败就回到 ① —— 判定标准本身可能有问题 │ ▼ ④ 把结论固化成可复核的证据 提交信息写「为什么」不只写「改了什么」 实验记录进 docs/，数字进核对器 失败也写进 docs/
这个闭环最关键的是第 ① 步。 很多用法是「让 AI 写代码 → 看着像对的 → 提交」。 问题在于「看着对」不是判定标准。

我自己的例子：让 AI 写了个弃答检测器（判断模型是否拒答），逻辑通顺。 但用 47 条评测集里的真实答案验证时，第一版漏 20 条，第二版误报 29 条 —— 改到第五版还在 0.787~0.957 之间震荡。

真正的问题不是「规则没写好」，而是「弃答是语义判断，不是字符串匹配」 —— 我一开始的整个思路就错了。最终改成复用已有的 LLM judge 基础设施。

如果第 ① 步就定义好判定标准，前四版根本不会存在。

验证机制：三道防线 + 两个核对器

机制解决什么怎么设计的
上下文指纹 判断「这轮评测是不是空跑」 只哈希检索结果，不含答案与分数 —— 否则分数一变指纹就变，空跑检测立刻失效
空跑阻断 防止把空跑的结论写进文档 指纹一致就报「不能作结论」而不是报「这是空跑」—— 只做阻断不做证明：阻断代价是多跑一次，漏报代价是写出错误结论
噪声底 判断差异是不是抖动 0.10 —— 单次 A/B 差值只是抖动幅度的下界，不是幅度本身。差值分布有方差，两次恰好接近不代表常态如此
事实核对器 保证文档里的数字不漂移 从数据源（不是从文档）重算关键数字，再回文档检查是否出现且一致。核对器自己不算进「我写了多少验证工具」
JS 语法门禁 防止「页面能开但点了没反应」 抽出 <script> 标签喂 node --check。检查「东西在不在」不等于检查「东西能不能用」
验收脚本最容易被忽略的一点：规则本身错了会让核对器变成只会刷 FAIL 的工具， 而一个老在报错的检查工具，用两次就没人信它了。 所以我的核对器区分「没写」（跳过，那是信息缺失）和「写错」（FAIL，那才是数据错误）。

verify_story_numbers.py 最初报过 FAIL（脚本按目录数是 55 个、 文档写 54 个）—— 我没有把它藏起来，也没把规则改成永远通过。 FAIL 本身就是信息：它告诉我两处用了不同的计数口径。 现在两边口径统一了：57 个工具脚本， 文档里的测试数也同步为实测的 393 个。

但我保留这个检查脚本 —— 因为数字会漂。 今天不改口径，明天加一个测试文件，文档里的数字就又错了。

06 / Judgment

工程判断力

技术栈谁都会写，判断力才是差异。以下五件事是我在项目里真实做过的判断 —— 每件都能被追问下一层。

01

三轮评测全是空跑，而我把结论写进了文档

工程素养

连续跑了三轮评测，分数有涨有跌，看着挺合理，我就写了结论。

后来逐条比对检索结果，发现三轮的上下文逐字完全相同 —— 检索层压根没变，分数差异 100% 来自 LLM 打分随机性，实测抖动约 0.021。 而我当时观察到的变化是 0.004~0.021，全在抖动量级以内。

更糟的是我把这个结论写进了文档，而那个文档后来成了我面试时讲的素材。

补了三道机制：上下文指纹（只哈希检索结果，不含答案与分数 —— 否则分数一变指纹就变，空跑检测立刻失效）、 空跑阻断（指纹一致就报「不能作结论」而不是报「这是空跑」—— 我不保证指纹相同就一定是空跑，所以只做阻断不做证明； 阻断的代价只是多跑一次，指纹不同的漏报代价是写出错误结论）、 噪声底。

02

改一个常量，动了整个检索链路

技术深度

做精排 A/B 时，我发现一轮改动「零效果」—— 结果与前一轮逐位相同。 按经验这说明诊断方向错了，于是换了个方向试，依然零效果。

第三次我不再改参数，而是去看候选池重叠度， 发现 top5 完全相同仅 8/47、集合大变 13/47 —— 召回阶段就变了。

根因：_IDF_MAX 这个常量被 BM25 召回和精排排序共用了。 改一个数，同时动了两处。而我的 A/B 脚本里写的「只切精排这一个变量」是错的。 拆成两个独立常量后重跑，recall 更差 —— 证明我「BM25 被牵连」的猜测也是错的。

03

模型会编造法条号，可溯源率只有 20%

业务落地

做端到端 Demo 时我顺手做了溯源核对 —— 答案里引用的条款号，能不能在检索片段里找到？

结果 10 个问答里只有约 20% 可溯源。最严重的一条：

问：  消防救援机构有哪些职责
答：  ...第四条 / 第四十五条 / 第五十三条...

检索实际返回的片段里只有：
      第十五条 / 第六十条 / 第六十二条 / 第六十四条 / 第四十七条

四个条款号，三个是编的。而且同一问题跑两次结果还不同 —— 这是随机波动，不是稳定能力。

为什么这个发现比「准确率 100%」更有价值？ 消防执法文书有法律效力，编造的条款号会直接影响法律适用， 轻则文书被退回，重则执法依据站不住。 所以我不回避，而是把它讲清楚，并说明配套机制。

配套三道防线落地后，引用可溯源率从 20% 提升到 87%， 人工复核返工率同步下降 65%。 但我不说「问题解决了」—— 剩下的 13% 恰恰是最难的那部分： 模型确实不确定时，它是否知道自己不确定。 这也是我把弃答判定做成三态（可答 / 存疑 / 未知）的原因。

04

优雅降级把依赖缺失藏起来了

系统思维

Agent3 原本在 import 阶段就因缺 DASHSCOPE_API_KEY 抛 RuntimeError，导致无密钥时整个 Agent3 无法启动。

看起来是「优雅降级」，实际上是把依赖缺失变成了一个延迟爆炸的哑弹： 构建期完全静默，只有 run 才暴露； 而 agent2 还硬编码了 /home/geng/.../faster-whisper-small 和 D:\Docker\vosk\...，换机必然失效。

改为 require_dashscope() / require_baidu() 在实际调用时校验，硬编码路径改为配置项 + 平台探测。

同类问题还有：multimodal_orchestrator.py 虽标 legacy 但被 gateway 实际引用， 直接删会炸；shutil.rmtree 原本只在 try 内，异常时临时目录泄漏。 删除前必查引用 —— 这是那 8 阶段改造里最不起眼但最有用的一条规矩。

05

验证工具本身也需要被验证

方法论

我写了一整套验证脚本，但其中有三个脚本自己出过 bug， 其中两个报的是假问题 —— 我去改了本来正确的代码。

后来我写了两个事实核对器：从数据源（不是从文档）重新算出关键数字， 再回文档里检查是否出现且一致。

设计上有两个刻意选择：
① 核对器自己不算进「我写了多少验证工具」 —— 它统计的目录里包含它，每加一个工具数字就变一次，文档永远「过期」； 更糟的是那个数字会变成「我什么时候跑了这个核对」。
② 区分「没写」和「写错」 —— 文档没提这项就跳过（信息缺失，不是数据错误）， 提了但对不上才 FAIL。
因为规则本身错了会让核对器变成只会刷 FAIL 的工具， 而一个老在报错的检查工具，用两次就没人信它了。

这五件事串起来是同一类问题：我以为我知道自己在做什么，其实不知道。

区别只在于，我后来学会了在优化之前先验证测量方法本身是有效的。
